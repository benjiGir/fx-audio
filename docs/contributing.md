# Contributing

```sh
pnpm install
pnpm lint         # oxlint
pnpm format:check # oxfmt (pnpm format to fix)
pnpm typecheck    # TypeScript 7
pnpm coverage     # unit tests, coverage thresholds: 95%
pnpm test:browser # real browsers through Playwright (all three engines by default)
pnpm api          # public API against the reports committed in api/ (pnpm api:update after a deliberate change)
pnpm mutation     # mutation testing with Stryker, break threshold: 80% (about 12 minutes, not run in CI)
pnpm build
pnpm check:package
pnpm changeset    # describe a change for the changelog (see Releasing)
pnpm bench:size   # bundle size against Howler, see the benchmark page
pnpm bench:play   # cost of play() against Howler, in a real Chromium
pnpm docs:dev     # this site, with live reload (generates the API reference first)
pnpm docs:build   # the site as it is published
```

## Browser tests

Browser tests run on Chromium, Firefox and WebKit. Sound is rendered with an `OfflineAudioContext`, so no output device is needed.
Locally, install them with `pnpm exec playwright install`, or restrict the run with `FX_BROWSERS=chromium`
(and `CHROMIUM_PATH` to use an existing Chromium binary).

## Mutation testing

Mutation testing changes the source on purpose (flips a condition, drops a call, empties a string) and checks that a unit test
fails each time. A mutant that survives is behaviour no test pins down. It takes about 12 minutes, so it is not part of CI:
run it by hand before a release or after a change to the core. The HTML report is written to `reports/mutation/index.html`.
Vitest is pinned to 4.1.x because Stryker's Vitest runner does not support Vitest 5 yet.

## Frozen API

The public surface of every entry point (`fx-audio`, `fx-audio/promise`, `fx-audio/node`, `fx-audio/testing`, `fx-audio/react`) is written to
`api/*.api.md` by API Extractor, and CI fails when the built declarations no longer match. A pull request that changes a signature
has to update those files, so the change shows up in review. `test/api.test.ts` pins the signatures users write code against
with type tests, checked by `pnpm typecheck`.

## Writing these docs

The code samples of the guides are real files in `docs/examples/`, included into the pages and compiled by `pnpm typecheck`.
Change the file, not a copy in the Markdown.

The [API reference](/api/) is generated by TypeDoc from the TSDoc comments of `src/`, so a better comment is a better
reference. Add an `@example` to what deserves one. `pnpm docs:api` regenerates it into `docs/api/` (not committed).
TypeDoc reads the TypeScript compiler API, which TypeScript 7 does not ship, so `.pnpmfile.cjs` gives it TypeScript 5.9,
as it does for Stryker. `scripts/typedoc-plugin.mjs` moves the members of Effect services onto their class and hides what
classes inherit from Effect.

## Releasing

Versions follow [Semantic Versioning](https://semver.org), and the public API is frozen (see above), so a breaking change is a major version.

1. Every pull request that changes what users get adds a changeset with `pnpm changeset`: pick patch, minor or major and write one line. The file in `.changeset/` is committed with the pull request.
2. To release, run `pnpm changeset:version`. It consumes the changesets, bumps `package.json` and writes `CHANGELOG.md`.
   Edit the new section of the changelog if it needs context: it is the body of the GitHub release. Preview it with `pnpm release:notes`.
3. Run `pnpm mutation` by hand, then open a pull request with the version bump and merge it.
4. Run the **Release** workflow (Actions tab) with the version. It checks `package.json`, builds the package, creates the tag `vX.Y.Z` and the GitHub release with the changelog section as notes, and attaches the tarball `fx-audio-X.Y.Z.tgz` that users install from (see [Getting started](/guide/getting-started)). Run it again for a version already released and it only rebuilds the tarball from the tag and uploads it.

Nothing publishes to npm yet: no workflow runs `changeset publish`, so a release is a tag, a GitHub release and a tarball.
